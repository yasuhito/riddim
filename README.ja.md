# Riddim

[English](README.md) | 日本語

Riddim は、[Pi](https://pi.dev) のスーパーバイザーにコーディング作業を頼み、
[Herdr](https://github.com/herdrdev/herdr) 上のワーカーに分担させるツールです。
ワーカーはそれぞれ別の Git worktree で編集し、コミットします。
スーパーバイザーは作業を調整して変更をレビューし、その版をローカルの `main` に
取り込んでよいか、あなたに確認します。

使い方は、スーパーバイザーに作業を頼み、変更と検証結果を確認し、取り込みを承認する、
という流れです。作業中も同じ会話から進捗を確認したり、指示を変えたりできます。

Riddim は Pi 専用で、作業はローカルで完結します。push、プルリクエストの作成、
リモートでのマージはしません。
[Firstmate](https://github.com/kunchenguid/firstmate) の一部を実装したもので、
PR パイプライン、secondmate、リモートホーム、クォータに応じた振り分け、
Pi 以外のエージェント実行環境は対象外です。

## 1. 必要なツールを準備する

次のものが必要です。

- Ruby。開発とテストでは **3.4.10** (`mise.toml`) を使います。他のバージョンは
  このリポジトリでは検証していません。CLI は Ruby の標準ライブラリで動きます。
- Git と、1 つ以上のコミットとローカルの `main` ブランチがある作業対象プロジェクト。
- **0.8.0 以降**の Herdr クライアントと、起動済みの Herdr サーバー。
  ターミナルペインを開いておきます。このバージョンは起動時の最低条件であり、
  以降のすべての Herdr リリースを検証したという意味ではありません。
- PATH 上で `pi` として実行でき、モデルに接続できる Pi。
  [Pi のセットアップガイド](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/quickstart.md)
  に従って準備してください。
- プロセスの確認に使うシステムの `ps` コマンドと、ワーカーを安全に片付けるための `lsof`。

Riddim を起動するシェルで、ツールを確認します。

```sh
ruby --version
git --version
pi --version
command -v herdr ps lsof
```

作業を任せる前に、信頼できるディレクトリで Pi を対話モードで起動してください。
`/login` で対応プロバイダーに認証し、`/model` で利用できるコーディング用モデルを選びます。
ファイルを書き換えない小さな質問をして応答を確かめ、`/quit` で終了します。
独自の接続先が必要なプロバイダーは、先に Pi 側で設定してください。
Riddim はプロバイダーや認証情報を設定しません。

環境変数で認証情報を渡す場合は、Herdr のワーカーペインで動く Pi からも
その変数を参照できる必要があります。別のシェルでログインできても、ワーカーが
認証できるとは限りません。Riddim は任意のシェル変数を新しいペインへ転送しません。

## 2. 起動プロファイルを設定する

Riddim はソースのチェックアウトから直接実行します。シェルで新しいディレクトリに
clone するか、既存のチェックアウトを使ってください。

```sh
git clone https://github.com/yasuhito/riddim.git
cd riddim
```

**Riddim のチェックアウト**で、Git の管理対象外のプロファイルを作成します。
ファイルやシンボリックリンクがすでにある場合は変更しません。

```sh
if [ ! -e config/agent-profile ] && [ ! -L config/agent-profile ]; then
  cp config/agent-profile.example config/agent-profile
fi
```

エディターで `config/agent-profile` を開きます。コメント以外の行は 1 行にし、
空白で区切った 3 つのトークンを書いてください。

```text
pi <provider/model> <effort>
```

プレースホルダーを、手元の Pi で使えるモデルと、`low`、`medium`、`high`、`xhigh`、
`max` のいずれかに置き換えます。付属のサンプルは
`pi openrouter/z-ai/glm-5.3-flash max` です。このモデルへのアクセス権が必要で、
Pi のインストールだけでは使えません。モデルが対応する思考の強度を選んでください。

このプロファイルから、新しいワーカーと `riddim supervise` で起動するスーパーバイザーに
`--model` と `--thinking` を渡します。`pi` を直接起動する場合は、Pi 自身のモデル設定を
使います。CLI を使うだけなら Bundler によるインストールは不要です。

## 3. Pi を起動する

Riddim 自体の作業をスーパーバイザーに任せるには、起動済みの Herdr セッションで
シェルペインを開きます。

```sh
cd /path/to/riddim
pi
```

初回起動時は Pi のプロジェクト信頼確認を読み、許可してください。
Git で管理している拡張が非公開の `state/` ディレクトリを初期化し、Pi の PATH に
`riddim` を追加します。スーパーバイザーの指示を読み込み、通知の監視も開始します。
`supervise` コマンドや、監視を有効にする手動操作は不要です。
空でない `RIDDIM_STATE_DIR` で保存先を指定していれば、その設定を使います。
この直接起動は、通常の Riddim チェックアウトのルートに限ります。
リンクされたワーカー用 worktree や、`RIDDIM_ACTOR` が空でないセッションは
スーパーバイザーになりません。上記の Ruby、Git、設定済みの Pi のモデルへのアクセス、
Herdr、ワーカーの起動プロファイルは引き続き必要です。
別の監視プロセスがすでに所有している場合は、置き換えずに起動を拒否します。

### 別のプロジェクトの作業を任せる

起動済みの Herdr セッションでシェルペインを開きます。
Riddim のチェックアウトではなく、**作業対象プロジェクトのチェックアウトのルート**へ
移動してください。ローカルの `main` を使い、自分の変更は先にコミットするか、
別に保存しておきます。

```sh
cd /path/to/your-project
git branch --show-current
git status --short
/path/to/riddim/bin/riddim supervise
```

2 つのパスは実際の絶対パスに置き換えてください。ブランチの確認では `main` と表示され、
status では何も表示されない状態にします。Riddim はローカルの HEAD からワーカーを
起動します。fetch や、未コミットの変更のコピーはしません。

`supervise` はプロファイルと実行中の Herdr セッションを確認し、同じペインで Pi を
起動します。スーパーバイザーの指示と通知拡張を読み込み、スーパーバイザーの PATH に
`riddim` を追加します。作業対象のプロジェクトに拡張をインストールしたり、
監視プロセスを手動で起動したりする必要はありません。

Pi が作業対象のプロジェクトを信頼するか尋ねたら、設定を確認してから許可してください。
プロジェクトのリソースを読み込んでワーカーを起動する際、Riddim は新しい worktree の
正確なパスを Pi の信頼ストアに永続的に登録します。親ディレクトリは登録しません。
worktree が分離するのは Git の編集です。**ファイルシステムへのアクセスや認証情報は
分離しません**。ワーカーはあなたのユーザー権限で動きます。
コードと Pi のリソースを信頼できるプロジェクトでのみ、作業を任せてください。

Herdr への呼び出しは `HERDR_SESSION` を使い、未設定なら `default` を使います。
複数のセッションを使う場合は、起動前に対象を選んでください。
既定では、この Riddim チェックアウトの `config/` に設定を、`state/` に非公開の
実行記録を保存します。別の保存先を使う方法は [CLI リファレンス](docs/cli-reference.md)
を参照してください。

## 4. 最初の作業を頼む

スーパーバイザーの Pi の会話に、範囲を絞った依頼を書きます。たとえば次のように頼めます。

> docs-example という名前の local-only ワーカーを 1 つ起動して、このプロジェクトの
> README にテストの実行例を短く追加してください。ワーカーにはコマンドを検証し、
> ドキュメントだけを変更してコミットさせてください。差分をレビューし、何を確認したか
> 教えてください。取り込む前に、レビュー済みのこの版を承認するか私に確認してください。
> push や PR の作成はしないでください。

スーパーバイザーはタスクを準備し、フォーカスを切り替えずに、バックグラウンドの
Herdr ワークスペースでワーカーを起動します。プロジェクト名が `my-app` なら、
ワーカーは `<worktree-root>/my-app-<repository-id>/docs-example` と、
ブランチ `riddim/docs-example` を使います。全プロジェクトの保存先は、Riddim の元の
インストール先と同じ親ディレクトリにある `.riddim-worktrees` です。
たとえば `~/src/riddim` なら `~/src/.riddim-worktrees` に保存します。
リンクされた Riddim CLI から起動しても、この保存先は変わりません。
Riddim リポジトリの外に置くことで、そのプロジェクト指示がワーカーに混ざるのを防ぎます。
Pi は対象プロジェクトとグローバルの指示を通常どおり読み込みます。
ID はローカルの Git 共通ディレクトリの正規パスから決まるため、同名の別クローンは混ざりません。
既存ワーカーは記録済みのパスを使い続け、移動しません。
既存の名前、worktree、ブランチは上書きしません。Ruby 標準ライブラリと Git だけを使い、
Treehouse や worktree のプールは導入しません。
あなたはスーパーバイザーとの会話を続けられます。タスクファイルを書いたり、
ワーカーの報告コマンドを自分で実行したりする必要はありません。

進捗の確認や方針の変更も、普段の言葉でスーパーバイザーに伝えてください。
スーパーバイザーは出力を確認し、指示を送れます。ただし、送信できたことは、
ワーカーが指示を読んだ証拠ではありません。ワーカーが idle になっても完了ではありません。
ワーカーが判断を求めたら、スーパーバイザーを通じて答えてから作業の再開を待ってください。

## 5. レビューし、ローカルへの取り込みを承認する

ワーカーが完了を報告すると、スーパーバイザーはコミット済みの差分、テスト、
引き渡しの状態を確認します。変更内容、実際に検証したこと、制約を示したうえで、
レビュー済みのこの版を取り込んでよいか、あなたに確認します。
`done` の報告や `ready` の結果だけでは、正しさも承認も確定しません。

示された内容を確認し、必要なら修正を頼んでください。
スーパーバイザーによる具体的な取り込みの提案には、たとえば次のように答えられます。

> レビュー済みのこの版の docs-example を、ローカルの main に取り込むことを承認します。

コミットハッシュを読んだり、復唱したりする必要はありません。
スーパーバイザーは、レビューしたコミットの完全な ID を提案とあなたの回答に結び付けて
記録します。この ID はレビューの記録で確認できます。
作業を任せる許可は、取り込みの承認ではありません。取り込みのたびに、あなたの明示的な
承認が必要です。`main` が進んだ後の rebase を含め、候補のコミットが変わった場合は、
スーパーバイザーが再度レビューし、結果と検証内容の変化を説明して、改めて承認を求めます。
結果が変わらなくても、この手順は必要です。

承認後、スーパーバイザーはローカルの `main` を、記録したコミットそのものへ
fast-forward できます。両方のチェックアウトに未コミットの変更がないことが条件です。
履歴が分岐していたら rebase して、再度レビューする必要があります。
スーパーバイザーは取り込みが実際に成功したか報告します。
ワーカーの片付けは取り込み後に限ります。ペインを閉じ、変更の残っていない worktree と
マージ済みのブランチを削除します。自動で push したり PR を作ったりはしません。
後から変更を公開する作業は、この手順の対象外です。

ワーカーを停止しても、その作業は破棄しません。未取り込みの作業を捨てるには、
確認したワーカー、世代、コミット、ファイルのスナップショットに対して、
**元に戻せない損失を別途明示的に承認する必要があります**。
取り込みの承認は、破棄の許可にはなりません。
[破棄時の安全確認](docs/cli-reference.md#discard-abandoned-local-only-work-with-separate-approval)
を参照してください。

## リファレンスとトラブル対処

- [CLI リファレンス](docs/cli-reference.md) には、コマンドの構文、設定と状態の保存先の選択、
  報告、通知、診断用の確認コマンド、片付けの制約を記載しています。
- [スーパーバイザーの契約](docs/supervisor.md) は、スーパーバイザーの責務を定める正式な文書です。
- [運用バックログ](docs/operational-backlog.md) は、既知の制約と過去の障害の記録です。
  追加のセットアップ手順ではありません。

起動や指示の送達を確認できない場合は、再試行の前に、残っているペインや記録などを
スーパーバイザーに調べてもらってください。拒否を回避するために worktree や記録を
削除してはいけません。通知の監視が失敗を報告したら、スーパーバイザーに復旧手順に
従うよう頼んでください。監視プロセスが動いていても、すべてのワーカーの状態を
読み取れている証拠にはなりません。

## 開発

`yasuhito/riddim` 自体の変更は、
[スーパーバイザーが行う PR 手順](docs/repository-development.md)に従います。
ローカルへの取り込みより先に PR を公開し、CI の成功を確認したうえで、レビューした
コミットのマージについて人間の明示的な承認を得ます。この方針を導入する際の一度限りの
ローカル取り込みと、スーパーバイザーの指示の再読み込みが前提です。
これは外部コマンドを使うスーパーバイザーの手順であり、CLI の PR 機能ではありません。
ワーカーと他のプロジェクトには、上記の local-only の規則が引き続き適用されます。

**Riddim のチェックアウト**で、指定の Ruby とテスト用の依存関係をインストールし、
ユニットテスト、使い捨ての環境での CLI シナリオ、Gherkin のチェック、RuboCop、
通知テストの型チェックを実行します。開発には Node >=22.19.0 と npm も必要です。
`test/support` の独立したパッケージには開発用の TypeScript と Node の型だけを置きます。
CLI の実行時依存関係は増えません。

```sh
mise install
bundle install
npm --prefix test/support ci --ignore-scripts
bundle exec rake
```

対象を絞って確認するには、次を実行します。

```sh
bundle exec rake typecheck
bundle exec ruby -Itest test/notification_session_race_test.rb --verbose
bundle exec rake lint
```

型チェックは現在の七つの `.mts` 通知シナリオと、小さなテスト用インターフェースを対象にします。
誤った API 呼び出しを拒否するコンパイル専用の回帰テストも含みます。
Node は型を除去して直接実行します。動的に読み込む拡張との境界は型チェックの対象外です。
本番の拡張と Pi の全 API の互換性や、実際の Pi の動作を確認するものではありません。
CI には Pi のパッケージをインストールしません。

PATH 上に `pi` があれば、実際の Pi を使う通知テスト、定期プロンプトテスト、ワーカー起動テストも自動で
実行します。独立した Pi 設定とローカルのループバックモデルを使い、認証情報は不要です。
Pi がない場合はスキップを報告します。Pi を入れない CI ジョブも同様です。
それ以外のテストは引き続き実行します。Pi をインストールした環境で、起動時の
ロック競合に関する回帰テストを確認するには、次を実行してください。

```sh
bundle exec ruby -Itest test/pi_worker_startup_test.rb --verbose
```

期待する結果は 1 テスト、11 アサーション、スキップなしです。
スキップしたテストでは、実際の Pi の起動を検証したことにはなりません。
